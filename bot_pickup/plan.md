## 1. Контекст

Бот офисного самовывоза для The Place: меню → корзина → оформление → заказ уходит на кухню →
сигнал «почти готово» → выдача по номеру заказа. ИИ нет. Оплаты в MVP нет. Источник правды —
Quick Resto и его БД; в v0 меню берём из локального `data/menu.json` (зеркало).

**Целевой путь доставки заказа на кухню — платное закрытое API Quick Resto** (подтверждено
поддержкой; звонок запрошен). Операционно это проще всего: бот делает **исходящий** вызов в QR,
заказ попадает на кассовый планшет, дальше QR **сам** печатает кухонный билет на кухонном АТОЛ и
фискализирует на кассовом — отдельный агент/принтер на месте не нужен. **Печать в MVP (v0-print) идёт
по пути C — отдельный ESC/POS-принтер + локальный агент** (решение от 2026-06-02); закрытое API —
целевой апгрейд (v1.1). До v0-print заказы дублируются в Telegram-чат кухни; всё строится mock-first
(конституция §2).

## 2. Ключевые решения и обоснование

| Решение | Выбор | Почему |
|---|---|---|
| Платформа бота | **aiogram 3.x** (3.28.x), обычные inline-клавиатуры + FSM | актуальная ветка; кастомная логика корзины/опций прозрачнее, чем во фреймворке диалогов. `aiogram_dialog` v2 — опционально, если боล boilerplate станет много |
| Хранилище FSM/корзины | **Redis** (`RedisStorage`) | состояние переживает рестарты/деплои (конституция §3) |
| БД | **PostgreSQL** + **SQLAlchemy (async, asyncpg)** + **Alembic** | заказы, клиенты, статусы, очередь печати. Меню в БД **не** храним — это внешний источник правды |
| HTTP-клиент | **httpx** (async) | вызовы Точка API и Quick Resto API |
| Конфиг | **pydantic-settings**, из окружения | без секретов в коде (конституция §4, §6) |
| Доставка заказа на кухню | **адаптер `OrderSink`**: `EscPosPrinter` (печать MVP, путь C) + `TelegramStaffChat` (всегда, бэкап) + `QuickRestoTerminal` (закрытое API — целевой апгрейд v1.1) | абстракция позволяет строить на моке/Telegram-чате сейчас и переключать канал печати без правки бизнес-логики (конституция §3) |
| Оплата | **заглушка** `NoPayment` в MVP; `TochkaSbp` позже | в MVP денег нет (spec §8) |
| Деньги внутри | в **копейках** (int) | корректность под будущую оплату; меню в рублях → конвертация |
| Деплой | **Docker Compose** (bot + Postgres + Redis) на **VPS в РФ** | 152-ФЗ (храним имя клиента), простота |
| Приём апдейтов | dev — **long-polling**; prod — **webhook** (aiohttp) | для closed-API инбаунд не нужен; webhook понадобится для ESC/POS-агента и вебхука оплаты Точки |

## 3. Архитектура

Один серверный процесс (на VPS): aiogram-диспетчер + (в prod) aiohttp-веб-сервер.

```
        Telegram ─┬─ клиент ─┐
                  └─ чат кухни ┘
                         │ apdates
                 ┌───────▼─────────────────────────────────┐
                 │  bot_pickup (VPS, РФ)                    │
                 │  handlers → services → repositories      │
                 │   ├─ MenuSource (json→sheet→quickresto)  │  чтение меню
                 │   ├─ Cart (Redis/FSM)                    │
                 │   ├─ OrderService (+ нумерация, статусы) │  Postgres
                 │   ├─ OrderSink[] ──────────────┐         │
                 │   └─ PaymentProvider (stub)     │         │
                 └─────────────────────────────────┼─────────┘
                                                   │
        ┌──────────────────────────────┬───────────┴───────────────┐
        ▼ (основной)                    ▼ (всегда)                  ▼ (запас)
  Quick Resto закрытое API        Telegram-чат кухни          ESC/POS-принтер
  (заказ→планшет→печать+чек)      (дубль заказа)              через локальный агент
```

- **Хендлеры тонкие**, бизнес-логика в сервисах и ничего не знает про Telegram (конституция §4).
- **Чтение меню** идёт через `MenuSource` (в v0 — JSON-файл; в v1 — Quick Resto открытое API).
- **Доставка заказа** — фан-аут по списку включённых `OrderSink`. Сигнал «почти готово» и статусы —
  собственная логика бота (не зависят от sink).

## 4. Модель данных (PostgreSQL)

Меню в БД не дублируется. Снимки (`*_snapshot`) фиксируют, что и по какой цене заказали — меняющееся
меню не должно мутировать прошлые заказы. Статус заказа хранится **строкой** (значения — app-enum
`OrderStatus`, §9), чтобы миграции не зависели от `ALTER TYPE` PG-енумов.

- **clients** — `id`, `tg_user_id` (uniq), `name`, `created_at`.
  *Имя спрашиваем один раз (FR-5) и переиспользуем.*
- **orders** — `id` (uuid), `order_number` (короткий, см. §4.1), `client_id` (fk),
  `status` (enum, §9), `pickup_time` (nullable), `total_kopecks` (int), `comment` (nullable; **не
  в v0** — в spec нет драйвера, заводим в later/P3), `created_at`, `updated_at`.
- **order_items** — `id`, `order_id` (fk), `menu_item_id` (строковый id из меню),
  `title_snapshot`, `unit_price_kopecks_snapshot`, `qty`, `options_snapshot` (jsonb: выбранные
  опции + дельты), `addons_snapshot` (jsonb, nullable: приложенные допы — id/название/кол-во/цена,
  FR-18), `line_total_kopecks`.
- **order_status_history** — `id`, `order_id` (fk), `status`, `at`, `actor` (staff tg_id / `system`),
  `note` (nullable). *Аудит смены статусов (FR-11).*
- **print_jobs** *(только для ESC/POS-пути)* — `id`, `order_id` (fk), `payload` (text),
  `status` (`pending`/`printed`/`failed`), `attempts`, `created_at`, `printed_at` (nullable).
- **daily_counter** *(для нумерации)* — `day` (date, pk), `last_number` (int).

### 4.1. Номер заказа

Короткий человекочитаемый номер для выдачи (FR-7, US-A5). Реализация: **счётчик, сбрасываемый
ежедневно**, формат `NNN` (зелёное-padding, 3 цифры). Берём атомарно (`INSERT … ON CONFLICT … DO
UPDATE … RETURNING` по `daily_counter`). При >999 заказов/день — расширяем до 4 цифр. Номер уникален
в пределах дня; этого достаточно, т.к. заказы дневные.

## 5. Внутренняя модель меню и источник

Pydantic-модели, повторяющие схему `data/menu.json` (конституция §3 — схема = внутренняя модель):

- `OptionChoice { id, title, price_delta_kopecks }`
- `OptionGroup { id, title, required, max_choices, choices: [OptionChoice] }`
- `MenuItem { id, category, title, description, serving, price_kopecks, available, options: [group_id], addons: [item_id] }`
- `Category { id, title, sort }`
- `Menu { currency, categories, option_groups: dict[group_id → OptionGroup], items, addon_category, addon_offer_categories }`

**Допы (FR-18).** Доп — обычная позиция (в категории `addon_category`, напр. `kitchen_addons`),
поэтому продаётся и самостоятельно. Какие допы предлагать к позиции: явный `MenuItem.addons`
(список id) переопределяет; иначе — весь пул допов, если категория позиции входит в
`addon_offer_categories` (для v0 — все «еды», без напитков). В JSON блок `addons`:
`{ "category": "...", "offer_to_categories": [...] }`. Доп в строке корзины — `{addon_item_id: qty}`;
цена строки = (цена позиции + дельты опций + Σ цена допа × кол-во) × кол-во строки.

**Соответствие `menu.json` ↔ модель (важно для загрузчика).** `option_groups` в JSON — это
**словарь, ключ = id группы** (сам объект группы поля `id` не содержит); `JsonFileMenuSource`
подставляет ключ как `OptionGroup.id`. Поля цен в JSON — `price` и `price_delta` **в рублях**; при
загрузке конвертируем в `*_kopecks` (rub→коп). Лишние верхнеуровневые ключи (`_note`, `version`,
`source`, `price_units`) загрузчик игнорирует.

**Контракт источника:**
```
class MenuSource(Protocol):
    async def get_menu(self, force_refresh: bool = False) -> Menu: ...
```
Реализации: `JsonFileMenuSource` (v0), `SheetMenuSource` (v0.1), `QuickRestoMenuSource` (v1 —
открытое API, `warehouse.nomenclature.dish`, Basic Auth; маппинг «толстого» JSON в нашу модель).
Поверх — **кеш** (Redis или in-memory) с TTL (например, 60 с) — меню не дёргается на каждое нажатие
(конституция §8). Стоп (`available=false`) приходит из источника. **Перепроверка доступности при
оформлении (FR-16) читает свежие данные мимо кеша** (`get_menu(force_refresh=True)`) — иначе на живом
источнике (v1) проверка станет фиктивной (в v0 источник — файл, стоп не меняется, но контракт держим).

## 6. Контур кухни — `OrderSink`

```
class OrderSink(Protocol):
    async def send(self, order: Order) -> SinkResult: ...
```
`OrderService` после создания заказа вызывает все включённые sink'и (список в конфиге). Реализации:

- **`QuickRestoTerminalSink` — основной.** Исходящий вызов в **закрытое (платное) API** QR: заказ →
  кассовый планшет; дальше QR штатно печатает на кухонный АТОЛ и фискализирует. Параметры (эндпоинт,
  формат payload, авто-печать на кухню) уточняем на звонке (research §8) — до этого это заглушка по
  согласованному контракту.
- **`TelegramStaffChatSink` — всегда включён (бэкап, FR-15).** Шлёт заказ в выделенный Telegram-чат
  сотрудников с inline-кнопками статуса (§9). Гарантирует, что кухня видит заказ, даже если основной
  канал лёг.
- **`EscPosPrinterSink` — запасной путь.** Кладёт `print_job` в очередь; **локальный агент** в кофейне
  (отдельный мини-сервис, см. §6.1) тянет задания и печатает через `python-escpos`. Нужен, только
  если закрытое API не подключаем.

Сигнал «почти готово» и статусы клиенту — отдельный механизм бота, не часть sink.

### 6.1. Локальный агент печати (только для ESC/POS-пути)

Нужен лишь если идём через свой принтер, а не через закрытое API. Принтер on-site за NAT, наружу не
выставляем. Агент держит **исходящее** соединение к серверу: long-poll `GET /agent/print/next` →
печать через `python-escpos` (`Network(host):9100` или USB) → `POST /agent/print/ack`. Задания копятся
в `print_jobs`, печатаются при возврате связи. При закрытом API этот компонент **не нужен**.

## 7. Оплата (заглушка → Точка, v1.1)

```
class PaymentProvider(Protocol):
    async def create_payment(self, order: Order) -> PaymentResult: ...
```
MVP — `NoPaymentProvider` (заказ оформляется без оплаты). Позже `TochkaSbpProvider`: динамический QR
(`Register Qr Code`, сумма в копейках) → клиенту `payload`-ссылка → вебхук `incomingSbpPayment`
помечает заказ оплаченным. Фискализация — через закрытое API QR (заказ на терминал) либо libfptr10
на АТОЛ (research §4). Рефанд части заказа (FR-17) — здесь же.

## 8. Пользовательский путь (FSM) и UX

Состояния (FSM, Redis): `Registration`, `Browsing`, `ItemConfig`, `Cart`, `Checkout`.

1. **Регистрация** (один раз): нет имени → спрашиваем → `clients.name`. Дальше пропускаем.
2. **Меню**: список категорий → позиции категории → карточка позиции (название, серьвинг, цена,
   описание; если есть опции — выбор групп) → «добавить в корзину».
3. **Корзина**: список строк, изменить количество, удалить, «оформить».
4. **Оформление**: (опц.) время самовывоза → подтверждение → **перепроверка стопа (FR-16)**:
   если позиция ушла в стоп — заказ не создаём, говорим какая, ведём в корзину. Иначе — создаём заказ,
   присваиваем номер, фан-аут в sink'и, показываем клиенту **номер заказа** + подтверждение.
   **Идемпотентность:** двойное нажатие «Подтвердить» не создаёт второй заказ (гасим повтор на время
   обработки / по ключу корзины; конституция §4).
5. **Статус**: клиент видит активный заказ; получает пуш «почти готово» и смену статусов.

**UX-бюджет (конституция §7):** типовой заказ — минимум шагов; на каждом шаге понятно, что дальше;
везде «назад»/«в начало»; обязательное подтверждение перед оформлением; нейтральные короткие тексты
(модуль `texts/`). Число шагов до оформленного заказа меряем на тесте с реальными людьми.

## 9. Жизненный цикл статусов заказа

`new → accepted → almost_ready → ready → handed_out`; ветка `rejected` (с причиной) — терминальная.

- Клиент инициирует `new` (оформление).
- Сотрудник кнопками в чате/основном канале: `accepted` (принят), `almost_ready` («почти готово» →
  пуш клиенту, FR-9/10), `ready`, `handed_out`, либо `rejected` (с причиной).
- Каждая смена пишется в `order_status_history`; клиенту отражаются значимые (принят / почти готово /
  готов / отклонён).

## 12. Деплой и хостинг

- **VPS в РФ** (Selectel/Timeweb/Beget), дата-центр РФ (152-ФЗ), ~2 vCPU / 4 ГБ (research §7).
- **Docker Compose**: контейнеры `bot`, `postgres`, `redis`. Миграции Alembic на старте.
- **Dev**: long-polling, без публичного URL. **Prod**: webhook (aiohttp), HTTPS; тот же aiohttp-сервер
  обслуживает `/agent/print/*` (если ESC/POS) и `/webhook/tochka` (позже).
- Бэкапы Postgres — заложить (у провайдера обычно платно).

## 13. Нефункциональные требования

- **Отклик** на действие ≤ ~1–2 с; тяжёлые операции — с «обрабатываю…» (конституция §8, FR/§6 spec).
- **Офлайн-устойчивость**: клиентский путь хостится вне кофейни и не зависит от её интернета (FR-14);
  при ESC/POS-пути задания печати копятся и допечатываются.
- **Безопасность/ПДн**: храним только имя + tg_id; секреты в окружении; ПДн не в логах/URL (конституция §6).
- **Тесты** (конституция §5): юниты на расчёт корзины с опциями, нумерацию, переходы статусов,
  стоп-перепроверку; внешние API (QR, Точка) замоканы.

## 14. Открытые зависимости (не блокируют старт разработки)

- **Закрытое API QR** — цена/условия, формат payload, авто-печать на кухню + фискализация (звонок,
  research §8). До ответа `QuickRestoTerminalSink` — заглушка по согласованному контракту; строим на
  `TelegramStaffChat` + мок.
- **Открытое API QR** — логин/пароль из Предприятие → Настройки (для `QuickRestoMenuSource`, v1).
- Доступы/реквизиты: `BOT_TOKEN`, `STAFF_CHAT_ID`, VPS, (позже) Точка API.
