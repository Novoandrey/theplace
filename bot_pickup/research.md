## 1. Вопрос ресёрча

Как с минимальной сложностью собрать ТГ-бота офисного самовывоза: меню → корзина →
оформление → передача на кухню → сигнал «почти готово» → статус. ИИ не требуется. Оплата
(СБП) — отдельной фазой, но архитектуру под неё нужно понимать заранее, чтобы не
переделывать.

## 4. Оплата и СБП (для будущей фазы v1.1)

Платёж и фискальный чек — **две разные вещи**, и их нужно разводить явно (конституция §6).
У эквайринга кофейни — Точка Банк, поэтому приоритетный путь — оставаться в их контуре.

### 4.1. Рекомендуемый путь — Точка Банк (их же банк)

**Оплата по СБП через Точка.API — подтверждено, методы есть.** Авторизация OAuth 2.0 / JWT,
разрешения `EditSBPData`, `ReadSBPData`. Поток под бота:
1. Один раз: регистрация ЮЛ и ТСП в СБП (`Register Legal Entity` → `Register Merchant`,
   `capabilities=111` — чтобы поддержать все типы QR без повторной регистрации).
2. На заказ: генерируем **динамический QR** (`Register Qr Code`, `qrcType=02`) с суммой
   корзины в **копейках**. В ответе — `image` (картинка QR) и `payload` (ссылка на оплату).
3. **Для бота удобнее слать `payload`-ссылку, а не картинку** — клиент уходит в приложение
   банка и платит. Это заодно **обходит ограничение нативных платежей Telegram** (которые не
   работают в desktop/web), что важно для офисных клиентов с компьютера.
4. Статус: вебхук `incomingSbpPayment` на наш URL (приходит при зачислении, с
   `refTransactionId`) — помечаем заказ оплаченным. Либо опрос `Get Qr Codes Payment Status`.
5. Возвраты по динамическому QR — через API (`Start Refund`), полные/частичные.
   - Альтернатива для фиксированного «кассового» сценария — **кассовый QR** (активируется на
     каждую оплату с суммой). Для нашего потока «сумма на заказ» проще динамический QR.
- **Комиссия СБП ~0,4% против ~2% по карте** — для кофейни заметная экономия.
- Деньги падают на их существующий счёт в Точке — отдельный провайдер (ЮKassa) не нужен.
- Песочница у Точки есть; докажем поток на ней.
- Источники: https://developers.tochka.com/docs/tochka-api/opisanie-metodov/sbp-sistema-bystryh-platezhej ,
  https://developers.tochka.com/docs/tochka-api/internet-acquiring-integration , https://tochka.com/professional-api/

**Фискальный чек (54-ФЗ): у кофейни уже есть АТОЛ-ККТ (на кассе и на кухне — фото от заказчика).**
Это меняет расклад — не обязательно арендовать облачную кассу, чек можно пробивать на их же
оборудовании, **если** существующая ККТ годится для интернет-расчётов (см. оговорку ниже).
- **Драйвер ККТ АТОЛ v10 (libfptr10)** работает из Python на Windows/Linux/macOS, у него JSON-API;
  чек регистрируется поэтапно (`ОткрытьЧек` → `ПечататьСтроку` → `ЗакрытьЧек`), поддерживаются и
  нефискальные документы, и HTTP-доступ через «Веб-сервер ДТО». То есть АТОЛ можно гонять кодом.
- Способы пробить чек по онлайн-оплате бота: **(а) через Quick Resto** — отправить заказ на
  кассовый планшет через их **закрытое (платное) API**, и фискализация пройдёт штатно на их АТОЛ
  (см. §5); **(б) напрямую через libfptr10** локальным агентом на машине, к которой подключена ККТ.
- **Оговорка по 54-ФЗ:** для интернет-расчётов (оплата без присутствия покупателя) ФР обычно
  должен быть зарегистрирован с признаком «расчёты в Интернете» и слать электронный чек на
  телефон/почту. Касса, зарегистрированная под расчёты «на точке», может для этого не подойти —
  **уточнить у их бухгалтера / АТОЛ / Точки**.
- **Облачная касса (запасной вариант):** Точка облачная касса автоматически формирует чек и шлёт
  в ОФД (ФН на стороне провайдера, по 54-ФЗ). Брать, только если существующую АТОЛ-ККТ нельзя
  использовать под интернет-оплаты.
  - https://tochka.com/knowledge/acquiring/chto-takoe-oblachnaya-kassa-i-kak-ona-rabotaet-prostoe-obyasnenie-dlya-biznesa/

**Что уточнить по фискализации:**
- Годится ли существующая АТОЛ-ККТ для интернет-расчётов (признак «расчёты в Интернете»), или нужен
  отдельный ФР / облачная касса?
- Если фискализировать через Quick Resto — есть ли у него вызов регистрации чека по API (§5, §8)?
- Точная модель АТОЛ и как она подключена (USB к ПК с QR / Ethernet / Веб-сервер ДТО) — от этого
  зависит, можно ли пробивать чек агентом напрямую.

**Про карты:** на кассе рядом с АТОЛ стоит отдельный банковский пин-пад (карты + бесконтакт) —
это текущий торговый эквайринг. СБП через Точку для бота — это про онлайн-оплату из чата, а не
замена этого пин-пада.

### 4.2. Запасные варианты (если у Точки чего-то не хватает)

- **Нативные платежи Telegram через провайдера** (`@BotFather` → `provider_token` →
  `sendInvoice` в копейках/`RUB` → `pre_checkout_query` + `successful_payment` → вебхук).
  Минус — **оплата в боте не работает в desktop/web Telegram, только в мобильном приложении**.
- **ЮKassa как провайдер** бандлит карту/СБП/SberPay + фискализацию (чеки формируются
  автоматически). Удобно, но это **отдельный от Точки контур** и второй договор.

### 4.3. Развилка по учёту (одинакова для Точки и ЮKassa)

Чек по этим продажам пробивается фискальным контуром банка/провайдера, **а не ККТ Quick
Resto**. Если кофейне важна единая картина продаж/остатков в POS — нужно отправлять продажи в
Quick Resto через их **платное закрытое API** (заказ → кассовый планшет, см. §5). Для соответствия
54-ФЗ цепочка Точки самодостаточна; для единого учёта в POS — закрытое API QR.

Для MVP это неактуально — **оплаты нет**. Фиксируем находку, чтобы фаза v1.1 не началась с нуля.

## 5. Quick Resto API — ОТВЕТ ПОЛУЧЕН (техподдержка, 2026-06-02)

У Quick Resto **два API**:

**1. Открытое API — бесплатно, всем облачным пользователям (любой тариф). Работа с бэк-офисом.**
- GET / POST / DELETE в/из бэк-офиса. В основном — сбор данных с облака и корректировка данных в
  разделах, описанных в их инструкции.
- Аутентификация — **Basic Auth**; логин и пароль для API лежат **на самом облаке**:
  Предприятие → Настройки → «Логин для API» / «Пароль для API».
- Документация: https://quickresto.ru/api/ . Вопросы — support@quickresto.ru.
- Этим мы **читаем меню/номенклатуру** (`warehouse.nomenclature.dish`, см. §6) и при необходимости
  пишем/правим back-office-данные (полезно для invoice-бота и дашборда — изучить, какие разделы
  доступны на запись).

**2. Закрытое API — платная услуга. Работа с кассовым терминалом.**
- Предназначено ровно под наш кейс: **отправка заказов из своих сервисов (бот/сайт) на кассовый
  планшет**, чтобы кассиры с ними работали (а оттуда — штатная печать на кухню и фискализация на
  их АТОЛ).
- Подключается отдельно и **платно**: нужно дать им телефон для консультации по закрытому API.

**Что это значит для бота:**
- «Нативный» путь *заказ → кассовый планшет → печать кухне на кухонном АТОЛ + фискальный чек на
  кассовом АТОЛ* **существует и официально поддерживается** — это и есть закрытое API. Но оно
  **платное** и требует отдельной договорённости. То есть это решение по деньгам/ценности (см. §7a,
  §4), а не технический тупик — что хорошо.
- Открытое API заказы на терминал **не отправляет** (оно про бэк-офис). Для приёма заказов именно
  закрытое.

**Прочее (без изменений):**
- Штатный ТГ-бот Quick Resto — клиентский, закрытый. **Не дублируем** (конституция §2): наша ниша —
  офисный приём с сигналом готовности.
- Встроенного ИИ/ML у Quick Resto нет (только ретроспективная BI). Для бота неважно; релевантно для
  роадмапа (прогноз — у iiko есть).
- В JSON номенклатуры видны `cookingPlace`/`prechecksTargetDevice`/`sendSignal` — подтверждает, что
  после попадания заказа в QR печать на кухню маршрутизируется штатно.

## 7. Хостинг и инфраструктура

- **Где:** бот — на внешнем сервере (интернет кофейни нестабилен; конституция §2, §3).
  Рекомендуем **VPS в РФ** у российского провайдера (Selectel / Timeweb / Beget) и **обязательно
  выбрать дата-центр в РФ** — потому что бот хранит ПДн клиента (имя, контакт/офис), а 152-ФЗ
  требует хранения ПДн граждан РФ на территории РФ. (У некоторых провайдеров есть и зарубежные
  локации — нам нужна российская.)
- **Конфигурация под нагрузку:** для aiogram-бота + Postgres + Redis + очередь печати с запасом
  хватает **2 vCPU / 4 ГБ RAM / 40–60 ГБ NVMe**.
- **Цены (РФ, проверено 2026-06-02):** базовый VPS (1 CPU / 1 ГБ / 20–25 ГБ NVMe) — от
  ~300–600 ₽/мес; средний сегмент (2–4 CPU / 4–8 ГБ) — ~800–1500 ₽/мес. Под нас реально
  уложиться в **~500–900 ₽/мес**. У Selectel — бесплатная DDoS-защита и 3 ТБ трафика; бэкапы
  обычно платны отдельно — заложить.
- **Покупать ли сразу:** для разработки v0 сервер не нужен (логика гоняется локально, Telegram
  можно слушать через long-polling без публичного URL). Но сервер **точно понадобится** для
  релея печати (§7a) и позже для вебхуков оплаты. Стоит дёшево — поэтому **взять небольшой VPS в
  РФ сейчас**, как стабильный staging/демо-эндпоинт; не переплачивать за мощность.
- Состояние диалогов — Redis; заказы и история — Postgres.

### 7a. Печать заказа на кухню (в MVP)

Требование: заказ из бота **печатается на кухне**. На кухне стоит **АТОЛ** (та же ККТ-модель, что
на кассе — фото от заказчика), а не простой чековый принтер. Две сложности: (1) бот off-site, а
устройство on-site за роутером (NAT) — выставлять его в интернет нельзя; (2) АТОЛ — это ККТ, и она
почти наверняка **подключена к Quick Resto** (QR ей управляет), а одну ККТ нельзя одновременно
дёргать из двух программ без конфликта.

Решение-принцип: **локальный агент в кофейне держит исходящее соединение к серверу** (long-poll /
websocket / MQTT), получает задание и печатает локально. Исходящее соединение проходит через NAT
без проброса портов; при обрыве — задания копятся на сервере и печатаются по возвращении связи.

Варианты (от самого чистого):
- **(A) Нативно через Quick Resto — самый чистый, но платный.** Отправляем заказ на кассовый
  планшет через **закрытое (платное) API** QR (см. §5), и он сам печатает кухонный билет на
  кухонном АТОЛ (`cookingPlace`/`prechecksTargetDevice`/`sendSignal`) и фискализирует на кассе.
  Один путь и для печати, и для чека, заказ сразу в учёте QR. Минус — платная услуга + отдельное
  подключение; и наш бот всё равно делает клиентский UX и сигнал «почти готово».
- **(B) Печать на АТОЛ напрямую через драйвер.** Драйвер ККТ АТОЛ v10 (`libfptr10`, Python,
  Win/Linux/macOS, JSON-API) умеет печатать **нефискальный документ** — то есть кухонный билет
  можно напечатать на АТОЛ как служебный текст. Но: устройство, скорее всего, занято Quick Resto,
  и делить одну ККТ между QR и агентом рискованно. Подойдёт, только если АТОЛ доступен агенту
  (отдельная машина / сетевой доступ / Веб-сервер ДТО) и не «залочен» QR.
- **(C) Отдельный дешёвый кухонный принтер для бота — рекомендуемый для MVP.** Поставить рядом
  обычный термопринтер ESC/POS 80 мм (ориентир 5–15 тыс ₽) и печатать на него из агента через
  `python-escpos` (`Network(host)`:9100 или USB). Не трогаем их ККТ вообще — ноль конфликтов, без
  платы за закрытое API. Минус — ещё одна железка и заказ не попадает в учёт QR (до перехода на A).
  Устройство-агент — Raspberry Pi (~5–8 тыс ₽) или уже стоящий ПК.
- **(D) PrintNode (turnkey):** их клиент на ПК/Pi в кофейне + печать по JSON-API. Free до 50/мес,
  далее ~$9/мес. Минус — зарубежный сервис и оплата в валюте (для РФ риск).

**Развилка (решение Андрея, цена vs единый учёт):** для MVP бесплатного discovery — путь **(C)**,
отдельный принтер: быстро, без зависимостей и платы. Когда захотим, чтобы заказы бота сразу падали
в учёт QR и фискализировались штатно — переходим на **(A)**, платное закрытое API. (B) — нишевый
запас.

**Что уточнить по закрытому API (для пути A):** цена/условия услуги; отправляет ли заказ на планшет
сразу печать на кухню (авто-fire) или нужно действие кассира; как при этом проходит фискализация.

**Бэкап-канал:** заказ всё равно дублируется в выделенный Telegram-чат кухни — если печать легла,
кухня всё равно видит заказы. **LTE-резерв** канала — чтобы печать на месте не зависела от
провайдера кофейни.

## 8. Открытые вопросы к Quick Resto (после первого ответа)

Главный вопрос (создание заказов) **закрыт**: открытое API — бэк-офис (GET/POST/DELETE, бесплатно);
закрытое API — заказы на кассовый терминал (платно). Осталось уточнить:

1. **Закрытое API:** цена и условия; отправляет ли заказ на планшет сразу печать на кухню (авто-fire)
