## 1. Контекст

Превращаем фото товарной накладной в готовый к импорту в Quick Resto документ прихода, с проверкой
человеком (шеф-повар) сомнительных мест. Источник правды — Quick Resto и его БД.

**MVP (v0) — это скилл внутри Claude Chat, без отдельной инфраструктуры и без ключа API.** Извлечение
из фото делает само зрение Claude в сессии; код-инструменты в сессии валидируют, сопоставляют с
номенклатурой и собирают файл импорта. Готовый файл шеф-повар импортирует в бэк-офис вручную.

**Telegram-бот — вне MVP, потому что у нас пока нет доступа к Claude API.** Боту нужен серверный
вызов зрения через Anthropic API; до его появления остаёмся в Claude Chat. Логика конвейера
(извлечение → проверка → сопоставление → пересчёт → файл) от поверхности не зависит и при появлении
API переносится в бота без переделок (`roadmap.md`). Всё строится mock-first (конституция §2): не
пишем в боевую кассу без подтверждённого write-API (конституция §6).

## 2. Ключевые решения и обоснование

| Решение | Выбор | Почему |
|---|---|---|
| Поверхность MVP | **Скилл Claude Chat** (SKILL.md + код-инструменты в сессии) | зрение даёт сам чат; нет ключа API, сервера и БД; самый дешёвый способ замерить точность (spec §7) |
| Извлечение из фото | **Зрение Claude в сессии** (v0); Anthropic API (v1, когда будет) | в v0 ключ не нужен; та же логика промпта переезжает на сервер для бота |
| Промежуточная модель | **Канонический JSON извлечения** (§5), деньги в копейках | стабильный контракт между извлечением и генерацией; от него — адаптеры под формат QR |
| Выход | **Файл импорта Quick Resto** (xlsx + csv, раскладка ПН135, §8) | приходная импортируется в бэк-офис; точная раскладка импорта — к проверке пробным импортом |
| Сопоставление | **Зеркало номенклатуры + таблица соответствий (aliases) + нечёткий матч + подтверждение** (§6) | ключ — артикул QR (research §5); подтверждения копятся, вопросов меньше со временем |
| Единицы | **базовая единица позиции из номенклатуры** + разбор упаковки из названия; объём→кг — лёгкий счёт/плотность/фасовка с подтверждением (§7) | в основном кг; пересчёт объёма неоднозначен → подтверждает человек (spec US-D2) |
| НДС | **берётся из накладной поставщика как есть** | 10%/22%/5% и пр. (research §5a); не нормализуем (spec FR-10) |
| Деньги внутри | **в копейках** (int); в файл импорта — в рублях | корректность расчётов; конвертация на выходе (конституция) |
| Хранилище состояния v0 | **файлы в репо** (`data/`, `samples/`) — БД нет | в v0 нет сервера; зеркало номенклатуры и aliases — JSON |
| Язык/тон | **русский, нейтральный** | конституция §2; spec FR-14 |
| Стек v1 (бот, later) | **aiogram 3.x + Docker + VPS в РФ**, переиспользуем паттерны `bot_pickup`, Anthropic API для зрения | гейтится на доступ к API; 152-ФЗ — VPS в РФ |

## 3. Архитектура (v0)

Конвейер в одной сессии Claude Chat; код-шаги — через исполнение кода. Человек (шеф-повар) — в петле
на проверке и подтверждениях.

```
  фото/скан/PDF накладной
          │
   ┌──────▼──────────────────────────────────────────────┐
   │  скилл bot_invoice (Claude Chat)                      │
   │                                                       │
   │  1) Извлечение (зрение Claude) ─────► канонический JSON│
   │  2) Валидация арифметики (validate_invoice.py)        │
   │  3) Сопоставление (match_nomenclature.py)             │
   │        ├─ aliases.json (соответствия, растёт)         │
   │        └─ nomenclature_qr.json (зеркало номенклатуры) │
   │  4) Пересчёт единиц + НДС                             │
   │  5) Вопросы по флагам ◄────────► шеф-повар (правки)   │
   │  6) Файл импорта (to_qr_import.py) ──► xlsx + csv      │
   └───────────────────────────────────────────────┬──────┘
                                                    │ вручную
                                            ┌───────▼────────┐
                                            │  Quick Resto    │
                                            │  Импорт приходной│
                                            │  → Провести      │
                                            └─────────────────┘
```

- **Извлечение и вопросы** ведёт Claude по инструкции `SKILL.md`; цифры/сверка/сопоставление/файл —
  детерминированные код-инструменты (ИИ не считает суммы — конституция §9).
- **Человек в петле:** подтверждает спорные сопоставления и пересчёты, правит флаги; без этого файл
  не считается финальным (spec FR-5, FR-11).
- **Источник номенклатуры** в v0 — выгрузка «Ингредиенты» (зеркало); в v1.1 — открытое API QR.

## 4. Конвейер по шагам

1. **Вход.** Одна накладная = одно или несколько изображений/PDF. Несколько страниц склеиваются в
   один документ.
2. **Извлечение.** Зрение Claude по чек-листу `SKILL.md` (поля шапки и строк ТОРГ-12) → канонический
   JSON (§5). Нечитаемые/перекрытые/спорные поля помечаются `confidence` и `note`.
3. **Валидация.** `validate_invoice.py`: построчно `кол-во×цена=сумма`, `НДС`, `с НДС=без НДС+НДС`;
   сверка 6 итогов; допуски на округление цены/ед. и НДС. Жёсткие расхождения → стоп до правки.
4. **Сопоставление.** `match_nomenclature.py`: сперва `aliases.json`, затем нечёткий матч по
   `nomenclature_qr.json`; для спорных/новых — вопрос человеку. Подтверждение пополняет `aliases`.
5. **Пересчёт.** Кол-во и цена → в учётную единицу позиции (из номенклатуры). Объём→кг —
   лёгкий счёт/плотность/фасовка, с подтверждением (§7). НДС — из накладной (§7).
6. **Вопросы.** Сводка флагов (низкая уверенность, неоднозначный пересчёт, артикул под вопросом,
   противоречивые массы) → человек правит/подтверждает.
7. **Файл.** `to_qr_import.py`: канонический JSON + сопоставления → файл импорта в раскладке ПН135
   (§8). Итоги файла сверяются с накладной.

## 5. Модель данных — канонический JSON извлечения (контракт)

Внутренняя модель извлечения (как `bot_pickup/data/menu.json` — внутренняя модель меню). Деньги — в
**копейках** (int). Версия схемы — в `schema_version`. Пример — `samples/EK-2029_extracted.json`.

- **source** — `files[]`, `doc_type` (например, «ТОРГ-12»), `okud`, `pages`, `printed_at`, `printed_by`.
- **document** — `number`, `date`, `basis`, `pay_by`.
- **supplier / shipper / consignee / payer** — `name`, `inn` (может быть `null`), адрес, банк.
  Поставщик (контрагент) может не иметь ИНН на бланке — берётся из справочника контрагентов QR.
- **items[]** — строки:
  - `n`, `name`, `supplier_code`, `supplier_article`
  - `unit`, `okei`, `qty_per_place`, `places`, `mass_gross_kg`, `qty`
  - `price_kop`, `sum_no_vat_kop`, `vat_rate`, `vat_sum_kop`, `sum_with_vat_kop`
  - `confidence` (`high|med|low`), `note`
  - `qr_nomenclature_match` (артикул QR или `null` — заполняется на шаге сопоставления)
- **totals** — `places`, `mass_gross_kg`, `qty`, суммы (`*_kop`), прописью, `vat_by_rate`.
- **extraction_flags[]** — человекочитаемые пометки (что проверить).

Правило: **финансовая строка авторитетна** (`кол-во×цена=сумма`); справочные `mass_*`, `*_place` —
вторичны и при противоречии помечаются, но не блокируют (spec FR-6).

## 6. Сопоставление с номенклатурой

- **`data/nomenclature_qr.json`** — зеркало номенклатуры The Place (выгрузка «Ингредиенты»: `art`,
  `name`, `unit`, `weight_kg`, `group`). 240 позиций. В v0 обновляется выгрузкой из бэк-офиса; в v1.1
  — чтением открытого API QR (`warehouse.nomenclature.*`).
- **`data/aliases.json`** — таблица соответствий «ключевые слова строки поставщика → артикул QR»
  (`keywords`, `art`, `qr_name`, `note`, `confidence`). **Главный растущий актив**: каждое
  подтверждение снижает ручную работу.
- **`tools/match_nomenclature.py`** — матчер: сперва `aliases` (точно), затем нечёткий матч по
  названию; топ-кандидаты с артикулом/единицей/группой. Спорные и «нет в номенклатуре» → вопрос.
- **Новые позиции** (нет в QR): не создаём автоматически (spec §8) — человек заводит в QR или
  пропускает строку.

## 7. Единицы, пересчёт и НДС

- **Учётная единица** — из карточки позиции QR (поле `unit`): в основном `кг`; исключения — `шт`
  (яйца, хлеб, упаковка) и `л` (часть масел).
- **Разбор упаковки** — из названия строки накладной (например, «(2,000 кг) упак.4 шт», «5 л / 4,7 кг»);
  кол-во упаковок × размер → базовая единица.
- **Объём → кг** (когда позиция в QR в кг, а накладная в л/мл): по согласованию — **лёгкий счёт**
  (1 л ≈ 1 кг), либо плотность, либо **фасовка** QR (л→кг). Любой неоднозначный пересчёт —
  **с подтверждением** (spec US-D2). Примеры зафиксированы в `samples/EK-2029_to_QR.md`.
- **Цена в файл — «с НДС» (ведущая):** `Цена с НДС = Сумма с НДС ÷ Кол-во`; `Сумма без НДС`/`Сумма НДС`
  — производные (формат QR, research §4). Несколько копеек расхождения от округления цены/ед. —
  норма; авторитетна сумма строки.
- **Ставка НДС** — из накладной поставщика как есть (spec FR-10).

## 8. Контракт формата импорта (раскладка ПН135)

Колонки строки документа (эталон — `samples/QR_pn135_format_sample.{xlsx,csv}`):

`№ · Артикул · Тип продукта · Наименование · Кол-во + ед.изм. · Цена с НДС · Сумма без НДС · НДС ·
Сумма НДС · Сумма с НДС` (+ в экспорте — `Стоимость доставки`, `Остаток`; для импорта не нужны).

- `Тип продукта` = `Ингредиент`; ед. = учётная единица позиции (в осн. `кг`).
- `НДС` — строкой вида `10.0 %`; деньги — в рублях с 2 знаками.
- Цена «с НДС» ведущая (§7); итоги файла = итоги накладной.
- **Доставка (2026-06-05):** StoreHouse XML в QR **не поддерживается** — путь закрыт, генератор и образцы
  удалены. xlsx/csv (ПН135) остаётся **человекочитаемым листом проверки / ручным запасом**. Основная
  доставка — создание приходной через **открытое API бэк-офиса** (объект `warehouse.documents.incoming` /
  `IncomingInvoice`, POST `/api/update`, basicAuth), **не затрагивая кассу**. Тот же канонический JSON →
  payload API; позиции приходной — отдельный объект (под разведку). Детали схемы — `research.md §4a`.

## 9. Проверки и обработка неопределённости

- **Арифметика** — `validate_invoice.py` (см. §4.3); жёсткие расхождения блокируют до правки.
- **Политика «спрашивать, не выдумывать»** (spec FR-5): нечитаемое/перекрытое/спорное → вопрос; не
  подставляем значение. Перекрытие штампом, правки ручкой, плохая печать → флаг.
- **Финансовая строка важнее справочных масс** (spec FR-6): при кривых `mass_*`/упаковке считаем по
  сумме строки и помечаем расхождение.
- **Чек-лист извлечения** в `SKILL.md` фиксирует частые места ошибок (единицы vs ОКЕИ, усечённые
  коды, брутто/нетто, штамп поверх бренда).

## 11. Нефункциональные требования

- **Точность извлечения** ≥ 95% строк без ручной правки сумм на реальной выборке (spec §7) — замер
  до платного этапа.
- **Сходимость итогов файла с накладной — 100%** (spec FR-13).
- **ПДн/реквизиты — не в логи**; собираем только необходимое (конституция §6; spec FR-15). В v0
  (скилл в чате) серверных логов нет; гигиена логирования — предмет **v1** (бот): не писать ПДн/
  реквизиты поставщика и покупателя в логи (задача под T027).
- Тексты/вопросы — русский, нейтральный тон.

## 12. Фазы поставки (детально — `tasks.md`; обзор — `roadmap.md`)

- **v0 — скилл Claude Chat** (этот план): `SKILL.md` + инструменты + данные; ручной импорт. Цель —
  точность и отладка сопоставления/единиц.
- **v1 — Telegram-бот** *(гейт: доступ к Anthropic API)*: тот же конвейер как сервис; зрение через
  API; правки спорных мест кнопками; стек как у `bot_pickup` (aiogram, Docker, VPS в РФ).
- **v1.1 — автопостинг** приходной через открытое API QR (гейт: доступна запись складских документов).

## 13. Открытые зависимости (не блокируют старт v0)

1. **Точная раскладка импорта QR** — проверить пробным импортом (§8).
2. **Доступ к Anthropic API** — гейт для v1 (бот).
3. **Запись складских документов через открытое API QR** — гейт для v1.1 (автопостинг).
4. Единичные пересчёты по позициям (вес отцеженного продукта и т.п.) — уточняются с шефом по ходу.
