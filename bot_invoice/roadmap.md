# roadmap — bot_invoice: путь MVP и интеграция

Как довести анализатор накладных от ручного скилла до бота с автопостингом в Quick Resto.
Тяжёлые задачи (точность зрения, сопоставление с номенклатурой, пересчёт единиц) одинаковы на
любом фронте — поэтому сначала решаем их в скилле, потом переносим в бота без переделок.

## Конвейер (один и тот же на всех фазах)

```
фото/PDF накладной
   → извлечение (vision-модель)            → канонический JSON (модель извлечения)
   → валидация арифметики                   → флаги/ошибки (validate_invoice.py)
   → сопоставление с номенклатурой QR        → артикул + базовая ед. на каждую строку
   → пересчёт кол-ва и цены (с НДС, базовая ед.)
   → вопросы по неуверенным местам          → правки человека
   → файл импорта QR (xls/csv в колонках ПН) [→ позже: автопостинг через API]
   → импорт/проведение приходной в Quick Resto
```

Меняется только **фронт** (Claude Chat → Telegram) и **последний шаг** (ручной импорт → API).

## Фаза 0 — MVP как скилл Claude Chat (сейчас)

Без инфраструктуры. Андрей кидает фото в чат → скилл извлекает, задаёт вопросы по сомнительным
местам, отдаёт лист проверки и файл импорта; Андрей правит и импортирует в бэк-офис вручную.

Состав скилла `invoice` (папка `/mnt/skills/user/invoice/` + хелперы здесь, в репо):
- `SKILL.md` — чек-лист чтения ТОРГ-12 / УПД / счёт-фактуры; политика «спроси, если не уверен»;
  правила маппинга в формат QR (цена с НДС ведущая; пересчёт упаковка→базовая ед.; ключ — артикул).
- `tools/validate_invoice.py` — сверка строк и итогов (уже есть, тест EK-2029 проходит).
- `tools/to_qr_pn.py` — генератор файла импорта в колонках ПН (xls/csv). *(после ответов по единицам)*
- `tools/match_nomenclature.py` — сопоставление строки → артикул QR (по справочнику/нечётко). *(далее)*
- `data/nomenclature_qr.json` — выгрузка номенклатуры The Place из QR (зеркало, читается API).
- `data/aliases.json` — таблица соответствий «поставщик → артикул QR», копится по ходу.

Цель фазы — замерить **точность извлечения** на реальной выборке (порог из конституции, напр.
≥95% по сумме) и отладить сопоставление/единицы. Это узкое место, не цифры.

## Сопоставление с номенклатурой — ядро интеграции

1. Один раз читаем номенклатуру The Place из QR (**открытое API**, Basic Auth): ингредиенты с их
   `Артикул`, названием, базовой единицей и фасовками. Кладём в `nomenclature_qr.json` (зеркало).
2. Матчер: строка накладной → ингредиент QR. Порядок: (а) точное совпадение по таблице `aliases`;
   (б) нечёткое по названию — предлагаем кандидатов; (в) человек подтверждает/выбирает новые/спорные.
   Каждое подтверждение пополняет `aliases` → со временем вопросов всё меньше.
3. Единицы/вес: из базовой ед. найденного ингредиента + размера упаковки (из названия или фасовки)
   переводим кол-во упаковок → базовую ед. и цену за упаковку → цену с НДС за базовую ед.

## Фаза 1 — Telegram-бот, выдаёт файл (когда скилл стабилен)

Тот же конвейер, но как сервис: персонал работает в Telegram, без Claude Chat. Архитектура — как у
`bot_pickup` (aiogram 3.x, Docker, VPS в РФ):

- сотрудник шлёт боту фото/PDF накладной;
- бот вызывает **vision-модель через Anthropic API** → канонический JSON (логика скилла переезжает
  на сервер: тот же промпт извлечения + `validate_invoice.py` + матчер);
- бот читает номенклатуру QR (открытое API, кеш) и сопоставляет; валидирует арифметику;
- бот показывает строки с inline-кнопками для флагов/спорных мест («стр.3 ед.: кг / шт?»,
  «сопоставить ‘Фарш’ → [Фарш говяжий 70/30] / другое»); сотрудник правит прямо в чате
  (переиспользуем паттерны подтверждения из `bot_pickup`);
- по подтверждению бот формирует файл импорта QR (xls/csv в колонках ПН) и отправляет его
  Андрею/менеджеру на импорт.

152-ФЗ: накладные содержат реквизиты поставщика/покупателя (покупатель — ИП, это ПДн) → VPS в
датацентре РФ (как у `bot_pickup`); ПДн не в логи/URL.

## Фаза 1.1 — автопостинг через API (убираем ручной импорт)

Если открытое API QR разрешает запись складских документов (нужно подтвердить, research §3), бот
сам создаёт приходную в QR. Человеку остаётся только просмотреть и **провести** её в бэк-офисе.
Если запись приходных через API недоступна — остаёмся на выдаче файла (Фаза 1) до появления пути.

## Фаза 2 — общий код в монорепо

Клиент QR и кеш номенклатуры выносим в `shared/` и переиспользуем в `bot_pickup` (чтение меню) и в
будущем супердашборде (остатки/выручка). Анализатор накладных → источник данных о закупках/
себестоимости для дашборда.

## Почему скилл раньше бота

Бот — это обёртка вокруг конвейера; ценность и риск — в извлечении, сопоставлении и единицах.
Их дешевле и быстрее отладить в Claude Chat на реальных накладных, а в Telegram перенести уже
проверенную логику. Параллельно копится `aliases` — главный актив, снижающий ручную работу.
```
v0 скилл (ручной импорт) → v1 Telegram (файл) → v1.1 автопостинг (API) → v2 общий код
```
