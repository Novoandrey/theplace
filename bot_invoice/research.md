# research — bot_invoice (анализатор накладных, Pilot 1)

Снимок ресёрча на 2026-06-05. Что выяснено по форматам Quick Resto, как ложится тестовая
накладная и какие вопросы открыты. Канон проекта — `../constitution.md`.

## 0. Идея MVP

Накладная (фото/PDF) → vision-извлечение → **файл для импорта в Quick Resto** + лист ручной
проверки. Первый шаг реализуем как **скилл для Claude Chat**: он извлекает позиции, задаёт вопросы
по неуверенным местам (плохая печать, правки ручкой) и отдаёт файл, который сотрудник
доимпортирует в бэк-офис. Без своего сервера/хостинга — самый дешёвый способ проверить точность
и ценность (конституция §2: mock-first, замеряемость; §6: не писать в боевую кассу без
подтверждённого write-API).

Целевой документ в Quick Resto — **Приходная накладная** (раздел **Склад → Складские документы →
Приходные накладные**): после проведения товары встают на склад и считается себестоимость.

## 1. WL API (присланный архив `qr-wl-api-docs`) — это НЕ про накладные

Архив описывает **клиентский** White-Label API: меню/номенклатура на чтение (`/wlcrm/dishes`,
`/wlcrm/mods`, стоп-листы, теги), заказы, **предзаказ** (создание заказа), профиль гостя. Это путь
для **bot_pickup** (заказ → касса), а не для прихода на склад. Для invoice-бота из него полезно
только понимание модели номенклатуры (ед.изм., НДС, группы) при будущем сопоставлении.

## 2. Quick Resto: приходная накладная — поля и импорт

Источник: `quickresto.ru/support/rabota_s_bek_ofisom/sklad/prikhodnye_nakladnye/` (стр. доступна
на fetch).

**Шапка:** № (авто, редактируется) · Дата поступления (можно = дате бумажной накладной) ·
Поставщик (из справочника **Контрагенты**; можно завести нового на лету) · Склад · Комментарий ·
Стоимость доставки. Авторасчёт: Сумма без НДС, Количество, Сумма с НДС, Сумма НДС. Есть флаг
**«Загружено из внешнего источника»** — т.е. импорт извне поддерживается.

**Строки (Элементы документа):** Наименование (из номенклатуры; новый товар можно завести) ·
Кол-во в ед.изм. · Цена с НДС · Сумма без НДС · НДС % · Сумма НДС · Сумма с НДС · Стоимость
доставки · Остаток. Важно: **Цена с НДС / Сумма без НДС / Сумма с НДС взаимозависимы** и
пересчитываются в обе стороны.

**Экспорт/Импорт** — пункт на верхней панели документа. Печатные формы (ТОРГ-12, ОП-12, ОП-5,
приходный ордер, счёт-фактура, требование-накладная) выгружаются в **.xls/.csv**.

**Путь 1С** (`/support/qr1c/exinv1cqr/`) — отдельная обработка «QR-1С», заливает поступления в
бэк-офис из 1С. Это не ручная загрузка файла; для MVP не нужен.

## 3. Открытое API (write) — на будущее, не для MVP

Из `../bot_pickup/research.md §5` (ответ техподдержки QR, 2026-06-02): открытое API — бесплатно,
**Basic Auth** (логин/пароль в Предприятие → Настройки), GET/POST/DELETE по бэк-офису. Им читают
номенклатуру (`warehouse.nomenclature.dish`) и, предположительно, можно создавать складские
документы. Это **целевой путь** для авто-постинга прихода (v1.1), но:
- какие именно складские разделы доступны на запись (POST приходной накладной) — **не подтверждено**;
- страница `quickresto.ru/api/` отдаётся JS-рендером, состав эндпоинтов из неё не вытащить fetch-ом.

Для MVP API не трогаем — отдаём файл на ручной импорт (конституция §6).

## 4. Формат импорта — ПОДТВЕРЖДЁН (образец ПН135, 2026-06-05)

Андрей прислал выгрузку приходной из бэк-офиса: `Приходные накладные — ПН135 — Элементы документа`
(xlsx и csv). Колонки строки документа:

`№ · Артикул · Тип продукта · Наименование · Кол-во + ед.изм. · Цена с НДС · Сумма без НДС · НДС ·
Сумма НДС · Сумма с НДС · Стоимость доставки · Остаток + ед.изм.`

Ключевые правила формата:
- **Цена «с НДС» — ведущая:** `Кол-во × Цена с НДС = Сумма с НДС`; `Сумма без НДС` и `Сумма НДС`
  вычисляются обратно по ставке. (В ТОРГ-12 наоборот — ведущая цена без НДС.) При маппинге:
  `Цена с НДС = Сумма с НДС ÷ Кол-во`.
- **Единица — базовая единица ингредиента** (в ПН135 всё в `кг`). Накладные часто в `шт` (упаковки) →
  нужен пересчёт упаковка→базовая ед. (или применение **фасовок** QR).
- **Тип продукта** = `Ингредиент` для сырья/товаров.
- НДС записан как `5.0 %`. xlsx хранит полную точность сумм, csv округляет до 2 знаков.

Точный шаблон *импорта* (в отличие от *экспорта*) стоит проверить пробным импортом: сгенерировать
файл в этих колонках и загрузить в тестовую приходную. Маппинг и пример — `samples/EK-2029_to_QR.md`.

**Уточнение (2026-06-05, итог): StoreHouse XML в Quick Resto НЕ поддерживается — путь закрыт.**
Со слов поддержки QR, кнопка импорта StoreHouse XML **устаревшая** и не работает; наши пробные
XML-варианты QR ожидаемо не принял. Генератор `to_storehouse_xml.py` и XML-образцы из репозитория
**удалены** — мёртвый путь не тащим. ПН135 (xlsx/csv, `tools/to_qr_import.py`) остаётся как
**человекочитаемый лист проверки / ручной запас**, а не формат загрузки.

**Доставка приходной — открытое API бэк-офиса (путь A, выбран 2026-06-05).** Поддержка QR прислала два
живых пути ввода накладных, оба в бэк-офисе и **без кассы**:
- **Открытое API** (`quickresto.ru/api`) — generic object-API: база `https://{layer}.quickresto.ru/platform/online/api/...`,
  Basic Auth, JSON, методы **GET и POST**; объекты адресуются через `moduleName`/`className` (чтение
  номенклатуры — `warehouse.nomenclature.dish`, подтверждено разбором rche.ru). Склад в числе доменов,
  создание приходной через POST в этой модели предусмотрено. **Выбран как основной путь доставки** (бывший
  FR-16/v1.1 — теперь основной). Не подтверждено публично и снимается разведкой `tools/qr_api_probe.py`
  (read-only) и/или вопросом в поддержку QR: точный `className` приходной, пример тела POST, и что **запись
  складских документов через открытое API разрешена** (часть объектов может быть read-only). Официальные доки
  `quickresto.ru/api` — JS-рендер и закрыты от автодоступа (robots), поэтому схему снимаем по живому слою:
  читаем существующую приходную list-эндпоинтом и реверсим поля.
- **DocsInBox** — нативная интеграция QR (Склад → Приходные накладные → Импорт накладных → Загрузка из
  DocsInBox) для накладных **по ЭДО**: платная подписка (цена индивидуальная, без публичного прайса),
  поставщик-центрична (1С/ЭДО/файл ТОРГ-12/УПД, **не** фото-OCR бумаги). Для бумажных/фото-накладных ниша
  `bot_invoice` сохраняется; для ЭДО-потока — родной путь QR. Открытый вопрос к команде: какая доля
  накладных The Place уже приходит электронно, а какая бумагой (определяет ценность Pilot 1).

Источники: открытое API — rche.ru (база/метод/объекты), `quickresto.ru/api` (JS, robots); DocsInBox —
`quickresto.ru/support/.../integratsiya_s_docsinbox/`, `wiki.dxbx.ru` (каналы приёма накладных),
тарифы `docsinbox.ru/price`.

## 4a. Открытое API — объект приходной накладной (ПОДТВЕРЖДЕНО доками QR, 2026-06-05)

Со скрина страницы `quickresto.ru/api` (прислал Andrey). Объект приходной:
- **Модуль:** `warehouse.documents.incoming`
- **Класс:** `ru.edgex.quickresto.modules.warehouse.documents.incoming.IncomingInvoice`
- **Эндпоинты** (basicAuth, `Content-Type: application/json`): `GET /api/list` — список (параметры
  `sortFields`/`sortOrders`/`filters`, тело `limit`/`offset`); `GET /api/read?objectId=N` — один объект
  **с подобъектами**; `POST /api/update` — создать/изменить (upsert: без `id` создаёт, с `id` правит);
  `POST /api/remove` — удалить. Ответы: 200 / 400 / 401 (auth).
- **Поля заголовка** (тело запроса): `documentNumber`* (№), `invoiceDate`* (дата поступления, date-time),
  `paymentDate`* (дата оплаты), `paid` (bool), `provider`* (объект `…warehouse.providers.Provider`),
  `store`* (объект `…warehouse.store.Store`, склад-получатель), `transactionAccount` (объект
  `…finances.tranaccounts.TranAccount`, счёт списания), `comment`, `processed` (bool — проведена ли),
  `totalSum` (с НДС, ₽), `totalSumWoNds` (без НДС), `totalNds` (НДС), `totalAmount` (суммарное кол-во),
  `id`, `lastUpdateDate`. (`*` — required.)

**Позиции ПОДТВЕРЖДЕНЫ (read id=136, 2026-06-05): приходят вложенно в поле `invoiceItems`** (массив).
Значит создание — один POST `/api/update` с шапкой + вложенным `invoiceItems`. Схема строки
(`invoiceItems[]`): `product` (объект номенклатуры, ссылка `{id}`), `measureUnit` (объект `{id}` — единица
строки), `actualAmount` (кол-во), `price`/`priceWithVat` (цена), `storeQuantity`/`storeQuantityKg`
(кол-во в ед. склада). Поля `calculated*`/`fixed*`/`costPrice*`/`prevPrice` — расчётные (сервер считает
сам; в create, скорее всего, не нужны — подтвердим тестом).

Снято разведкой по живому слою (2026-06-05):
- склад-получатель: `store.id = 1` («Склад 1») — единственный;
- поставщиков 17 (`provider.id` 1..17) — какой = поставщику накладной, мапим через `refs` (имя в `shortName`);
- внутренних `id` товаров в нашем экспорте номенклатуры НЕТ (только артикул) → тянем карту
  `article → product.id (+ measureUnit.id)` командой `map` по классу **ингредиентов**
  `warehouse.nomenclature.singleproduct` / `…singleproduct.SingleProduct` (плоский список с `article`,
  `measureUnit`, `id`, `barCode`, `code1C`). В `read` приходной id=136 первая позиция ссылалась на `Dish` —
  ссылка `product` полиморфна; для наших закупаемых ингредиентов класс `SingleProduct` (его className и
  пойдёт в payload). Класс `Dish` (`warehouse.nomenclature.dish`) — дерево групп (list отдаёт 4 корня:
  Технические/Кухня/Бар/BREAKFEST), для плоской карты не годится.

**Механика дерева номенклатуры (2026-06-05):** `list` (и Dish, и SingleProduct) отдаёт только корень —
группы (`SingleCategory`/`DishCategory`) + товары, лежащие в корне. `read` группы детей НЕ возвращает
(только поля самой группы; id=8 «Мясо, рыба…» — `SingleCategory`, массивов с детьми нет). Значит
дети-ингредиенты достаются фильтром `list` по `parentId` = id группы. Формат `filters` (query-параметр,
«Array of objects») — наши форматы фильтра открытое API **молча игнорирует** (возвращает корни). DevTools
показал: бэк-офис грузит детей группы через ВНУТРЕННИЙ data-эндпоинт
`/platform/data/{module}/select?parentContextId=N&parentContextClassName=…SingleCategory` — но он
**требует сессию (куки): на Basic Auth отдаёт 401**, для интеграции не годится. Итог: перечисление
ингредиентов через открытое API пока не решено — **вопрос к поддержке QR** (как через `/api/...` получить
детей группы / плоский список SingleProduct / формат `filters`). Создание приходной от этого НЕ зависит:
путь `POST /api/update` валидируем отдельно тестом с известным id товара (напр. «Вода» id=194, unit_id=2),
не дожидаясь полной карты.

**Форма создания (clone из приходной id=136, 2026-06-05):** позиции ссылаются на товар классом **`Dish`**
(не `SingleProduct`): id 309/310/311/314/382/411, measureUnit id=4. В ответе `read` объект `store`
приходит БЕЗ `className` (null) — при создании className склада надо подставлять (CN_STORE). Минимальный
payload с `SingleProduct` дал 500/NPE — вероятная причина: ссылка `product` должна быть классом `Dish`.
Следствие для постера: карта нужна **`article → Dish.id`**; уточняем у поддержки, как получить
плоский список/детей класса `Dish` с артикулами.

Открытые вопросы (под тест create; до явного «ок» — только read):
1. Минимальный набор полей строки/шапки для create (что обязательно, что сервер считает сам) — снимаем
   пробным POST тестовой приходной (`processed=false`), затем `read` назад и `remove`.
2. Проведение: создать с `processed=false` (черновик на проверку) → провести отдельно/выставить `true`.

**БЛОКЕР ПОДТВЕРЖДЁН (2026-06-05): создание приходной через open API не проходит.** `POST /api/update`
с корректным payload стабильно даёт HTTP 500 / NPE в `PrimeCostCalculator.setStoreDocumentItemStoreState`
(`PrimeCostCalculator.java:348`), вызов из `CRUDSupportService.expandMapDependencies` →
`AbstractItemPersistenceService.updateTransientFields` при чтении позиции назад внутри `updateEntity`
(в транзакции → откат, ничего не создаётся). NPE НЕ зависит от: null-классов (убраны), класса товара
(`Dish`/`SingleProduct`), наличия `vat`, флага `processed` (false/true). Read/list/remove существующих
накладных работают. → серверная сторона; вопрос оформлен в `support_question.md`. Инструмент
`qr_create_test.py clone` умеет `--items N` / `--processed` / `--no-items` для воспроизведения.
Карта `артикул→id`: из read накладной 139 (ПН135) получены 13 живых `SingleProduct.id` (артикулы
6,7,90241,54,5,90100,17,16,19,18,30,37,84 → id 9,10,370,54,7,214,17,16,19,18,31,37,84; unit=2 кг, vat id=4 5%).


## 5. Сопоставление с номенклатурой — ключ = «Артикул» QR

Образец ПН135 показал ключ строки — **Артикул номенклатуры QR** (6, 7, 90241…), а не код поставщика
из накладной (`МС-…`, `ЕК-…`). Значит, каждую строку надо связать с артикулом ингредиента в QR.
Варианты:
- таблица соответствий (alias) «строка поставщика → артикул QR», копится по ходу — основной актив;
- нечёткое сопоставление по названию к номенклатуре, прочитанной открытым API;
- ручной выбор/создание позиции при импорте (в UI приходной это есть) — запас на новые позиции.

Единицы: из базовой ед. найденного ингредиента + размера упаковки (из названия/фасовки) переводим
кол-во и цену в базовую ед. Подробно — `roadmap.md` (раздел «Сопоставление»).

## 5a. НДС 2026 — проверено

С 01.01.2026 (ФЗ № 425-ФЗ) базовая ставка НДС в РФ — **22%** (была 20%); 10% сохранена для
социально значимых товаров; **5%/7%** — спецставки УСН. Поэтому в EK-2029 ставки 10%/22% корректны,
а 5% в ПН135 — спецставка УСН (другой поставщик/регистр). Бот **копирует ставку из накладной
поставщика** и не «исправляет» 22→20.

## 6. Тестовая накладная EK-2029 (на её основе делаем тест)

Расшифрована с двух фото (ТОРГ-12, 11 позиций). Артефакты:
- `samples/EK-2029_extracted.json` — канонический JSON v0.1 (внутренняя модель извлечения,

  `с НДС = без НДС + НДС`, и сверка 6 итогов с напечатанными. Допуски на округление цены/ед. и НДС.

**Результат проверки:** все 11 строк и все итоги (мест 29, брутто 53,278, кол-во 33, без НДС

## 8. Ответ поддержки QR (2026-06-08) — РАБОЧАЯ схема create + перечисление номенклатуры
**Создание приходной — НЕ одним объектом, а раздельно (это снимает NPE PrimeCostCalculator):**
1. Шапка: `POST /api/create?moduleName=warehouse.documents.incoming` — только
   `documentNumber, invoiceDate, provider{id,className}, store{id,className}, paid`. В ответе — id.
2. Позиции по одной: `POST /api/create?moduleName=warehouse.documents.items.incoming` (ОТДЕЛЬНЫЙ модуль),
   тело `InvoiceItem`: `product, measureUnit, actualAmount, price, priceWithVat, vat, extraExpenses` +
   `parentItem{id=<id шапки>, className=IncomingInvoice}`.
