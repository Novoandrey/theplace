# research — bot_invoice (анализатор накладных, Pilot 1)

Снимок ресёрча на 2026-06-05. Что выяснено по форматам Quick Resto, как ложится тестовая
накладная и какие вопросы открыты. Канон проекта — `../constitution.md`.

## 0. Идея MVP

Накладная (фото/PDF) → vision-извлечение → **файл для импорта в Quick Resto** + лист ручной
проверки. Первый шаг реализуем как **скилл для Claude Chat**: он извлекает позиции, задаёт вопросы
по неуверенным местам (плохая печать, правки ручкой) и отдаёт файл, который сотрудник
доимпортирует в бэк-офис. Без своего сервера/хостинга — самый дешёвый способ проверить точность
и ценность (конституция §2: mock-first, замеряемость; §6: не писать в боевую кассу без
подтверждённого write-API).

Целевой документ в Quick Resto — **Приходная накладная** (раздел **Склад → Складские документы →
Приходные накладные**): после проведения товары встают на склад и считается себестоимость.

## 1. WL API (присланный архив `qr-wl-api-docs`) — это НЕ про накладные

Архив описывает **клиентский** White-Label API: меню/номенклатура на чтение (`/wlcrm/dishes`,
`/wlcrm/mods`, стоп-листы, теги), заказы, **предзаказ** (создание заказа), профиль гостя. Это путь
для **bot_pickup** (заказ → касса), а не для прихода на склад. Для invoice-бота из него полезно
только понимание модели номенклатуры (ед.изм., НДС, группы) при будущем сопоставлении.

## 2. Quick Resto: приходная накладная — поля и импорт

Источник: `quickresto.ru/support/rabota_s_bek_ofisom/sklad/prikhodnye_nakladnye/` (стр. доступна
на fetch).

**Шапка:** № (авто, редактируется) · Дата поступления (можно = дате бумажной накладной) ·
Поставщик (из справочника **Контрагенты**; можно завести нового на лету) · Склад · Комментарий ·
Стоимость доставки. Авторасчёт: Сумма без НДС, Количество, Сумма с НДС, Сумма НДС. Есть флаг
**«Загружено из внешнего источника»** — т.е. импорт извне поддерживается.

**Строки (Элементы документа):** Наименование (из номенклатуры; новый товар можно завести) ·
Кол-во в ед.изм. · Цена с НДС · Сумма без НДС · НДС % · Сумма НДС · Сумма с НДС · Стоимость
доставки · Остаток. Важно: **Цена с НДС / Сумма без НДС / Сумма с НДС взаимозависимы** и
пересчитываются в обе стороны.

**Экспорт/Импорт** — пункт на верхней панели документа. Печатные формы (ТОРГ-12, ОП-12, ОП-5,
приходный ордер, счёт-фактура, требование-накладная) выгружаются в **.xls/.csv**.

**Путь 1С** (`/support/qr1c/exinv1cqr/`) — отдельная обработка «QR-1С», заливает поступления в
бэк-офис из 1С. Это не ручная загрузка файла; для MVP не нужен.

## 3. Открытое API (write) — на будущее, не для MVP

Из `../bot_pickup/research.md §5` (ответ техподдержки QR, 2026-06-02): открытое API — бесплатно,
**Basic Auth** (логин/пароль в Предприятие → Настройки), GET/POST/DELETE по бэк-офису. Им читают
номенклатуру (`warehouse.nomenclature.dish`) и, предположительно, можно создавать складские
документы. Это **целевой путь** для авто-постинга прихода (v1.1), но:
- какие именно складские разделы доступны на запись (POST приходной накладной) — **не подтверждено**;
- страница `quickresto.ru/api/` отдаётся JS-рендером, состав эндпоинтов из неё не вытащить fetch-ом.

Для MVP API не трогаем — отдаём файл на ручной импорт (конституция §6).

## 4. Ключевой открытый вопрос — формат импорта

Андрей: «Quick Resto принимает storehouse XML на импорт». В публичных доках точная схема этого
XML **не описана**. Две гипотезы:
- (а) собственный XML бэк-офиса QR (пункт **Экспорт/Импорт** в документе);
- (б) формат **StoreHouse** (складская система UCS/R-Keeper) — отдельный продукт; возможно, QR умеет
  читать именно его XML. Термин «storehouse» неоднозначен.

**Что нужно от Андрея, чтобы зафиксировать формат (1 артефакт снимает все догадки):** выгрузить из
своего бэк-офиса **одну существующую приходную накладную через Экспорт/Импорт** — в XML, если такой
пункт есть; иначе в .xls/.csv. Этот образец станет эталоном схемы для генератора.

## 5. Второй ключевой вопрос — сопоставление с номенклатурой

Коды в накладной (`МС-…`, `ЕК-…`, `00000266`) — это **коды поставщика**, они не обязаны совпадать
с кодами/ID номенклатуры в Quick Resto The Place. Значит, каждую строку надо связать с позицией
склада QR. Варианты:
- сопоставление по названию (нечёткое) к номенклатуре, прочитанной открытым API;
- таблица соответствий (alias) «строка поставщика → позиция QR», накапливается по ходу;
- ручной выбор/создание позиции при импорте (в UI приходной это есть) — для MVP проще всего.

Зависит от того, по какому полю матчит формат импорта (имя? внешний код? внутренний ID?) — см. §4.

## 6. Тестовая накладная EK-2029 (на её основе делаем тест)

Расшифрована с двух фото (ТОРГ-12, 11 позиций). Артефакты:
- `samples/EK-2029_extracted.json` — канонический JSON v0.1 (внутренняя модель извлечения,
  деньги в копейках, поля confidence/note/qr_nomenclature_match);
- `samples/EK-2029_review.md` — лист ручной проверки (рубли, флаги «(?)»);
- `tools/validate_invoice.py` — валидатор: построчная сверка `кол-во×цена = сумма`, `НДС`,
  `с НДС = без НДС + НДС`, и сверка 6 итогов с напечатанными. Допуски на округление цены/ед. и НДС.

**Результат проверки:** все 11 строк и все итоги (мест 29, брутто 53,278, кол-во 33, без НДС
14 772,80, НДС 1 879,33, **с НДС 16 652,13**) сходятся; жёстких расхождений нет. Под ручную проверку
ушли только стр. 3 (ед.изм.) и стр. 9 (код) + ИНН поставщика. → vision-извлечение по такому
качеству фото работает; узкое место — не цифры, а **сопоставление с номенклатурой** и **формат
импорта**.

Канонический JSON — это и есть «толстая» модель извлечения; от неё будут идти адаптеры под формат
импорта QR (по аналогии с тем, как `bot_pickup/data/menu.json` — внутренняя модель меню).
